## 二、P1：397 剔除字中有 237 个「可立即重定位恢复」，却全部被送进 GAN 缺口

**核心发现（已做完整复现实验）：**
v2.4.0 的 `lead_strict_headwords.py` 只按「union 里该字当前框」判小字即剔除，**没有搜索
charalign14 里该字的其它候选框**——而项目自己的映射里，这些字大多还有字头级框可用：

| 逐级复核 | 数量 |
|---|---|
| 剔除 397 字中，charalign14 有「短边≥60px@150dpi」的其它框、且该框在最终字体中**空闲** | 309 |
| 其中通过项目自己的 v2.1 字头级判据（p90≥4.5 或 短边≥65@150dpi） | 238（233 基本区） |
| **再通过完整恢复链路（`vectorize_box` + 字形级 glyph_ok，与 v2.3.1 回填同款）** | **237（232 基本区）** |

- **强证据组（p90≥4.5，笔画确凿为字头级）：144 字（141 基本区）**，含
  呂/渝/澡/題/丞/咼/層/懲/冬/爲/姬/嬌/臺/澤/鶉/釵/鐃/祿/禱/艾/蓋/鍛/豕 等常用字；
- 尺寸过闸但笔画偏细、需内容复核的弱证据组：93 字（今/佞/卿/吟/宴/庭/拜/相/盲/枚/皿…，
  其 c14 框大而墨迹细，可能是宽松框包小字，需逐字确认）。
- 例证：呂 的 c14 框 02_0028R [1713,571,1809,672]（96×101@150dpi，p90=11.2）；渝 06_0074L
  [737,1325,822,1416]（85×91，p90=5.2）；題 11_0271L [342,475,425,555]（83×80，p90=5.2）——
  这些框在 union12（剔除脚本输入）与 v2.4.3 字体中都**未被任何字占用**。
- 复现命令：对 `v243-strict-report.json` 的 dropped_list 逐字执行
  「c14 替代框（框唯一性检查）→ p90 判据 → `font_norm.vectorize_box` → glyph_ok」，237 通过。

**影响**：
1. 「缺口 6,219 = GAN 补全目标」被高估约 **237 字**（其中 144 字证据强）；这 237 字不需要 GAN，
   用现成的重定位机制（v2.1 `lead_glyph_filter.py` 的替代框搜索 + v2.3.1 的回填 QA）即可恢复；
2. 其中含大量常用字（冬/爲/姬/嬌/臺/今/拜/相/枚/宴/呂/渝/題…），它们在 v2.0.x 里本来有可用字形，
   现在被计为「GAN 才能补全」的缺口。
**建议**：把「严格剔除」改为「先重定位、后剔除」——对每个候选剔除字先跑 c14 替代框搜索
（框唯一性 + p90/尺寸 + 矢量化 + glyph_ok，必要时加注文指纹复核），搜索不到再剔除。
预计可立即回收 ~144-237 字（覆盖 62.46% → 最高 ~63.9%），GAN 目标相应缩水。

## 四、P2：GAN 补全路线的前置合规缺口（前瞻性）

「缺口 6,219 = GAN 目标」目前**没有任何 GAN 代码/产物**（scripts/ 无 GAN 实现，work/ 无 GAN 资产），
是路线承诺而非在途功能。在 GAN 落地前建议先定三件事（写入 DECISIONS 并进 PROVENANCE.md）：
1. **provenance 标记**：GAN 字形必须在 manifest/provenance.json 标 `gan`（四态字段已有），
   且**不得计入 real**、不得计入「真迹覆盖率」——现有 `provenance_counts` 结构支持，但生成管线要保证；
2. **覆盖率口径**：真迹覆盖与「真迹+GAN 总覆盖」必须分栏披露，避免 62.46% → 100% 的跳跃误导；
3. **许可与训练数据**：GAN 若用本刻本字形+字头标注训练，衍生字形的 OFL 兼容性与
   「未使用第三方字库轮廓」声明的边界要提前书面化（README/PROVENANCE）。

## 五、P2：contours_override 机制实为「双重失效的死代码」（无害，但自审计的修复描述名不副实）

- `contours_override.json` 目前仅含 二/顔 二字，v2.4.3 字体中 **0 使用**（二字已随 397 剔除）✓ 无害；
- v2.4.1 的「门禁」是 `font_build.py` 读 `assigned[].src`/`label_source` 且须等于 `from_v201_glyph`；
  但现行 mapping 生成器（`lead_strict_headwords.py` 等）写出的 `assigned` 条目**只有 char+cand.box，
  没有 src 字段**（实测 mapping_verified_all13.jsonl）——即使未来某字重进 mapping，
  override 也永远不会命中。即：门禁从未真正接通过，所谓「仅 from_v201_glyph 时注入」在现格式下恒不成立。
- 建议：要么删掉 override 路径，要么让所有 mapping 写入器统一携带 src 标签并加单测；
  否则 GAN 时代若想用 override 固定字形，会踩同一个坑。

## 六、结论

v2.4.x 系列在**标准一致性**上迈了一大步：headword-only 原则落地（0 小字残留）、发布流程成熟
（数字自动生成、SHA 冻结、QA 同次执行）、文档/审计目录校订基本准确，第三轮报告的多数问题
（顔/二、smallsrc 披露、圈号账目）都已处置并留有清单。

本轮唯一实质性发现是 **§二**：397 剔除是一次「不搜索替代框的一刀切」，其中 **237 字
（144 字强证据、232 基本区，含大量常用字）用项目自己的 charalign14 映射 + 既有重定位机制
即可恢复**，却被计入了「GAN 补全」缺口——覆盖率的真实上限被低估约 1.4 个百分点，
GAN 的必要范围被高估。建议 v2.4.4 先跑「重定位优先」的回收（约 144 字可立即安全入库），
再谈 GAN。其余为台账归因（芡=芍、顔根因）与数字（46,815/46,817）的校订级问题，以及
GAN 落地的合规前置定义。
