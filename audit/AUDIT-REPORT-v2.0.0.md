## 二、P0：发布字体中确认存在的错误字形（同框复用 → 两个码位共用同一像素）

**事实链（全部复现）：**
1. `work/lead/confirmed_union7.json` 里 **114 个 (page,half,box) 被 2-3 个不同字符共用**（229 个字符条目）。
2. 其中 **99 个框上是「真正不同的字」**（用 Unihan 变体关系剔除异体对后），另 15 个是
   简繁/异体同形对（你/伱、值/値、嘘/噓、横/橫、济/濟、荣/榮 等）。
3. 字形缓存 `work/font/build/cache/` 与 v2.0.0 字体构建统计均确认：**这些框的矢量轮廓逐字节相同**
   （114/114 对轮廓一致、114/114 对 bbox 一致）——同一幅像素被打上两个不同标签装入 cmap。
4. 同一位置不可能同时是两个不同字头 → **99 个真冲突框保证至少 99 个错标字形**（约 0.5%）。
5. v1.2（union6）同类冲突仅 13 框；**v2.0 合并环节新增 101 框**（102 框涉及 vlm_fp 条目：
   ocr_pool×59、pool_loose×24、ocr×13、charalign9×4、?×2 与 vlm_fp_A/B 冲突）。
6. 我用本地 Qwen3-VL-2B 对 114 框裁图独立认字：**42 框读作旧标签**（→ 新 vlm 标签错，
   如 冲/𠖹、会/侌、团/㘞、慢/𢢔、标/柡、亲/𣐽、欧/𣢮、氰/𣱩…）、**1 框读作 vlm 标签**
   （底/厎）、**71 框两者都不是**（如 02_0167 框读作「壁」，而入库为 壓 与 壂——两侧都存疑）。
   即：错标同时存在于**新旧两侧**，并非只有旧挖字错。

**根因（两点叠加）：**
- 未确认列表取 charalign14 的框，而 union6 旧条目持 charalign9 的框；两版映射对同一框指派
  不同字，v2 合并时**没有任何「框唯一性」检查**，直接叠加；
- 指纹条存在「框底跨入下一字头注文区」的错位模式：框内是上一字头的字形，框下竖条却是
  下一字头的注文开头（常以「又【廣韻】…」开头，可通过音切开头过滤）→ A 类据此「确认」了错字。
  `font_qa.py` 只查渲染，无「同轮廓不同码位」检查，这类错误**全部漏检**。

## 三、P0：覆盖率口径混用 → 70.51% 高估，且 238 个非目标字冒充字头

1. 声明「11,681 / 16,567 = 70.51%」。但 16,567 来自 `work/seq/canonical.jsonl` 基本区目标字表，
   而分子 11,681 是**整个 U+4E00–9FFF 区**的入库数——其中 **238 个字不在 16,567 目标内**
   （全部来自 v0.9 `ocr_pool` 挖字：丛/乡/亚/亲/众/会/伞/你/值/台/吗/喵/嘘/团/国/在/奥/学…，多为简化码位）。
2. 因此：
   - 对目标字表真实覆盖 = **11,443 / 16,567 = 69.07%**（不是 70.51%）；
   - 真实剩余目标字 = **5,124**（文档写 4,886，同样因混用口径差 238）；
   - 若按「基本区块覆盖」口径应为 11,681 / 20,992 = 55.6%（发布包 README 自己写目标 cmap 是 20,992+42）。
3. README 自相矛盾：缺口解释称「简体新码点在 1716 字典中本无字头」，却把这 238 个简体码位
   作为「real 真迹」收录并计入覆盖率；其中 49 个还与 §二 的同框冲突叠加（错上加错）。

## 五、P1：验证集的方法学问题（97% 的可迁移性存疑）

1. **验证集不可复现**：60 条候选（`fp_validate_cands.json`）的选取过程无脚本、无文档；
   声称「已知正确字形」的确认方式没有记录；其中 **3 个 hint 根本不在 canonical 字表**
   （如「栖」）——这些字在 ±60 窗口里永远不可能被匹配到（只会拉低未过滤命中率 39/60）。
2. **「同规则」不成立**：`lead_vlm_fingerprint_val.py` 的候选范围是**整个部首段**
   （`chars[s["lo"]:s["hi"]]`），且只记录 top1/score，**不记录 top2/margin**。
   公布的「n=30、97%」实际是用 ±60 窗口另行离线复算得到的（我复算 29/30 吻合）——
   但按仓库里的验证脚本跑不出这个数。
3. **代表性偏差**：60 个字多为常用字（材/石/中/帝/余/朕/舅/孤…），注文长且独特；
   而生产对象以生僻字为主（注文常为「字彙補古文X字註詳X畫」之类短注）。常用字上的
   top-1 精度不能外推到生僻短注；验证集里甚至出现 2 例 score=1.0 的假命中（匽→區、蓼→𩼻），
   说明短注场景的碰撞率远高于 3%。
4. 该验证只覆盖「映射标签正确」的情形；B 类（映射错、指纹纠正）只有 24 例目检支撑，
   对 7,827 个入库 B 而言样本量不足（检出 0.5–1% 错误率需要数百例）。

## 六、P1：字体质量——679 个字形孔洞全失（合/冒/內/冬/乳 等常用字）

- `qa-report-v20.json` 的 `holes.lost=679`（其中基本区 228，含 合、冒、內、冬、乳、刑、危、參、双、召…），
  `holes.fewer=1,724`。我复跑渲染核对：乳/冬/合/內/冒/又 在 256px 下孔洞数=0（宋体参照 1–3 个）。
  冒（日+目 3 个孔洞全失）这类字实际渲染接近墨块。
- `font_qa.py` 有意把 holes 设为「仅记录、不参与判定」（QA.md 已说明，木刻允许笔画粘连）。
  设计可以理解，但**679 个（3.3%）且包含大量常用字**的规模未在发布说明里给出数量级，
  用户拿到的「QA PASS」与肉眼观感差距较大；且矢量化环节（font_norm）若能在轮廓层保留
  孔洞，多数可修复。

## 七、P2：核心生产步骤未入库（最大可复现性缺口）

- 仓库脚本只到 `lead_vlm_fp_full.py`（转写+top1）为止。以下环节**全部是手工/一次性执行，无脚本**：
  ① top2/margin 离线评分生成 `vlm_fp_scored.json`；
  ② 音切开头过滤（完整 marker 清单未落代码，实测含 正字通/廣雅/爾雅/釋名/佩觿/五音集韻 等）；
  ③ A/B 分类、去重与**冲突裁决**（B 先入、A 让位，123 个字由此易主，2 个被静默丢弃）；
  ④ union7 合并与 QA 剔除（138+2 的逐类分布只能事后推断）；
  ⑤ mapping_verified_all7.jsonl / manifest_v20.json 生成。
- RELEASE-NOTES 的「复算命令」跳过了这五步——按它无法重建 20,611 字体。
  模型（work/models/qwen3vl2b）与输入物均在，补一个脚本即可闭环。
- `vlm_fp_scored.json` 的 `top2/score2` 字段实为 top1/score 的复制（错标字段），
  文档「记录 top1/top2/margin」不实；margin 本身计算正确（top1−第二名）。
- `scripts/lead_vlm_fingerprint.py` 与 `scripts/lead_vlm_fingerprint_val.py` 是同一份代码的复制品。
- `kx_full.xlsx` 加载用 `setdefault` 只取同字首条注文（多部首同字 1,675 条被忽略），
  匹配窗口也只按首条位置展开——对多部首字有漏配风险。

## 八、改进方案（按优先级）

1. **加「同框唯一性」闸**（防 §二）：合并 union 时按 (page,half,box) 判重，冲突框二选一
   （建议取指纹/OCR 证据更强的一侧，另一方降级或除名）；`font_qa.py` 增加
   「不同 cmap 条目轮廓完全相同」检查，命中即 FAIL。
2. **修覆盖率口径**（§三）：分子与分母统一到 canonical 16,567；同时公开两种口径
   （目标覆盖 69.07%、基本区块覆盖 55.6%）。对 238 个 ocr_pool 简体码位专项复核
   （多数应为错标，且 49 个与同框冲突叠加），纠正或除名后重发覆盖率。
3. **把生产五步落成脚本**（§七）：固定 marker 清单、合并顺序、剔除理由，并在 scored 输出中
   记录 yq_pass/class/冲突裁决/剔除原因等字段；`top2/score2` 改为真第二名；删除重复脚本；
   `kx_full` 同字多条注文全部参与匹配。
4. **增强 A 类防错**（§二根因）：对条带顶部 N 像素做「字头级大墨块」检测——若条带开头
   就含字头尺寸字形（说明框底已跨入下一条目），则拒收该 A 类确认；或要求 top2 也具备
   音切开头才认 margin。
5. **验证与抽验升级**（§五）：验证集按生产分布重建（生僻字+短注为主）、在 val 脚本内
   实现 ±60 窗口与 margin 记录并文档化「已知正确」的来源；对 12,804 个新增字按
   A/B×margin 分层抽验数百例（当前 48 例只能支撑「错误率<6%」级别的说法）。
6. **孔洞质量**（§六）：在 `font_norm` 矢量化时做孔洞保留（内轮廓检测），至少对 228 个
   基本区 lost 字重做；发布说明里给出 holes.lost/fewer 的数量级，或把「常用字孔洞全失」
   提升为硬闸。
7. **provenance 语义**（§四）：manifest 的 `verified_by` 按 src 分别标注
   （如旧条目=OCR/序列对齐；A/B=指纹+音切+margin）；文档 A/B 数字改为「QA 前 x / 入库 y」双列；
   修正 13,000+、~8,900、~4,000 margin 三处表述。

## 九、结论

v2.0.0 的**主声明大体可复核**（计数、哈希、打包、过滤器存在性、验证集 97% 可复算），
但存在三类实质问题：
- **正确性**：114 个同框双标（99 个真冲突）保证 ≥99 个错标字形随包发布，且 QA 无法发现；
- **口径**：70.51% 覆盖率高估 1.44 个百分点，真实目标覆盖 69.07%、真实剩余 5,124；
  238 个非目标简体码位被计为「真迹字头」；
- **可复现性**：指纹评分→过滤→合并→QA 剔除的五个生产步骤没有代码，发布声明中的
  「复算命令」无法重建本版字体。

建议在修复 §二/§三 并补齐 §七 的脚本后，再发布 v2.0.1。
